## 1. 项目一句话定义

**Studio Javis** 是部署在工作室物理 Ubuntu 主机上、有"身体"（屏幕+机械臂+摄像头）、能管理整个工作室局域网（NAS / HomeAssistant / 虚拟机 / RSS / 日程）、能识别每位成员、有跨会话记忆的智能公告板系统。

- 平时横屏当桌面信息流；
- 唤醒后竖屏全屏对话，摄像头跟脸；
- 用户离开自动重置。

### 2.3 Docker 容器化与部署移植规范

> **本节是 Docker 目录格式、镜像构建、Compose 分层、Mac→Linux 移植的唯一权威。**
> D 维护所有 Dockerfile，其他三人只在自己 Dockerfile 里加依赖。

#### 2.3.1 Dockerfile 目录格式（强制）

每个服务的 Dockerfile 存放在 `infra/docker/` 下，**平铺命名，不嵌套子目录**：

```
infra/docker/
├── Dockerfile.api-gateway      # Python FastAPI 服务
├── Dockerfile.agent            # Python + OpenClaw + LLM
├── Dockerfile.perception       # Python + OpenCV + YOLOE
├── Dockerfile.web              # Node 构建 → Nginx 静态 serve
├── .dockerignore               # 忽略 node_modules / __pycache__ / .venv / .git
└── scripts/
    ├── entrypoint.sh           # 通用：等待 DB + 跑迁移 + exec CMD
    └── healthcheck.sh          # curl /health 或 pg_isready
```

**命名规则**：`Dockerfile.{service-name}`，与 Compose 的 `service.name` 对应。

#### 2.3.2 多阶段构建模板

**Python 服务（api-gateway / agent / perception）**：

```dockerfile
# ============ Stage 1: Builder ============
FROM python:3.12-slim AS builder
WORKDIR /build
RUN --mount=type=cache,target=/var/cache/apt \
    apt-get update && apt-get install -y --no-install-recommends build-essential
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    pip install uv && uv sync --frozen --no-dev

# ============ Stage 2: Runner ============
FROM python:3.12-slim AS runner
RUN groupadd -r javis && useradd -r -g javis -d /app javis
COPY --from=builder /build/.venv /app/.venv
COPY services/<name>/ /app/
COPY packages/ /app/packages/
COPY infra/docker/scripts/entrypoint.sh /entrypoint.sh
COPY infra/docker/scripts/healthcheck.sh /healthcheck.sh
USER javis
ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=5s CMD /healthcheck.sh
ENTRYPOINT ["/entrypoint.sh"]
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**前端（web）**：

```dockerfile
# ============ Stage 1: Builder ============
FROM node:22-alpine AS builder
WORKDIR /build
COPY pnpm-lock.yaml pnpm-workspace.yaml package.json ./
COPY apps/web/ apps/web/
COPY packages/ packages/
RUN corepack enable && pnpm install --frozen-lockfile
RUN pnpm --filter web build

# ============ Stage 2: Runner ============
FROM nginx:1.27-alpine AS runner
COPY infra/docker/nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /build/apps/web/dist /usr/share/nginx/html
EXPOSE 80
```

#### 2.3.3 Python 服务系统依赖清单

| 服务 | 额外 apt 包 | 备注 |
|------|-------------|------|
| `api-gateway` | 无（纯 Python） | 最轻，~150MB |
| `agent` | `libpq-dev` | psycopg2 需要 |
| `perception` | `libgl1-mesa-glx libglib2.0-0 libsm6 libxext6 libxrender-dev libgomp1` | OpenCV 运行时 |

**铁律**：不要在 Dockerfile 里装 `nvidia-cuda-toolkit`（体积爆炸）。perception 的 GPU 推理在 Linux 阶段通过 NVIDIA Container Toolkit + `--gpus all` 注入。

#### 2.3.4 Compose 分层规范

**三套 Compose，职责严格分离**：

| 文件 | 用途 | 数据库端口 | 网关端口 | 谁在用 |
|------|------|-----------|----------|--------|
| `docker-compose.yml` | Mac 本地开发 | 5432, 6379 | 8080 | 四人本地 |
| `docker-compose.test.yml` | CI + 集成测试 | 5433, 6380 | 8081 | CI / 手动 |
| `docker-compose.prod.yml` | Linux 生产 | 5432, 6379 | 443→8080 (Nginx) | Ubuntu 主机 |

**Compose 文件必须放在 `infra/compose/` 目录，不允许根目录散落。**

**开发 vs 生产关键差异**：

| 维度 | Dev | Prod |
|------|-----|------|
| 代码挂载 | `volumes: - ./services:/app` (bind mount, 热重载) | 无 bind mount（镜像自包含） |
| 前端 | `vite dev` (HMR) | Nginx 静态 serve |
| perception 摄像头 | host 进程（不进容器） | 容器 + `--device /dev/video0` |
| GPU | 无 | `deploy.resources.reservations.devices[0].capabilities: [gpu]` |
| restart | `unless-stopped` | `always` |
| 日志轮替 | `max-size: 10m` `max-file: 3` | `max-size: 100m` `max-file: 5` |
| 环境变量文件 | `.env.local` | `.env.production` |

#### 2.3.5 数据卷规范

```yaml
volumes:
  pgdata:           # PostgreSQL 数据 — 唯一需要持久化的卷
  redis_data:       # Redis RDB 快照（可选）
  uploads:           # 用户上传文件暂存（VM upload 用）
```

**禁止**：
- `node_modules` / `.venv` / `__pycache__` 进 Docker volume
- 数据库卷使用 bind mount（必须 Docker volume）

#### 2.3.6 镜像版本管理

```
# 开发阶段（每次 PR 合并）
studio-javis/api-gateway:dev-{git_short_sha}
studio-javis/agent:dev-{git_short_sha}
studio-javis/perception:dev-{git_short_sha}
studio-javis/web:dev-{git_short_sha}

# 发布阶段（打 git tag）
studio-javis/api-gateway:v0.1.0
studio-javis/agent:v0.1.0
```

GitHub Actions 在 PR 合并到 main 后自动 build + tag。**Linux 生产环境只拉 release tag 镜像，不拉 `:latest`。**

#### 2.3.7 Mac→Linux 移植流程

```bash
# 1. Mac 上构建 linux/amd64 镜像
docker buildx build --platform linux/amd64 \
  -f infra/docker/Dockerfile.api-gateway -t studio-javis/api-gateway:v0.1.0 .

# 2. 导出为 tar（或推到私有 registry）
docker save -o ./dist/api-gateway.tar studio-javis/api-gateway:v0.1.0

# 3. 传输到 Linux 主机后加载
scp ./dist/*.tar javis@<ubuntu-ip>:/opt/staging/
ssh javis@<ubuntu-ip> "docker load -i /opt/staging/api-gateway.tar"

# 4. 在 Linux 上启动生产栈
ssh javis@<ubuntu-ip> "cd /opt/studio-javis && \
  docker compose -f infra/compose/docker-compose.prod.yml up -d"
```

**移植检查清单**（D 负责逐项打钩）：
- [ ] Mac 上 `docker buildx build` 四个镜像全过
- [ ] Mac 上 `docker compose -f infra/compose/docker-compose.test.yml up` schemathesis 全绿
- [ ] 镜像传输到 Linux 主机且 `docker load` 成功
- [ ] Linux 上 `docker compose -f infra/compose/docker-compose.prod.yml up -d`
- [ ] `docker compose ps` 六容器（四服务 + PG + Redis）全部 healthy
- [ ] `curl localhost:8080/api/system/metrics` 返回 200
- [ ] 前端 `http://<ubuntu-ip>` 可访问
- [ ] perception 摄像头 `--device` 直通验证（Linux 阶段）

## 3. 共享接口契约

### 3.1 HTTP API（OpenAPI 规范，存于 `packages/contracts/openapi.yaml`）

| Method | Path | 拥有者 | 说明 |
|---|---|---|---|
| POST | `/api/auth/login` | D | 用户名密码登录，返回 JWT |
| POST | `/api/auth/refresh` | D | 刷新 token |
| GET | `/api/me` | D | 当前用户 + 偏好 |
| PATCH | `/api/me/preferences` | D | 更新喜好 |
| GET | `/api/users` | D | 工作室成员列表（管理员） |
| POST | `/api/chat/sessions` | B | 创建会话 |
| POST | `/api/chat/sessions/:id/messages` | B | **SSE 流式响应**，见 §3.2 |
| GET | `/api/chat/sessions/:id/messages` | B | 历史消息 |
| GET / POST / DELETE | `/api/feeds` | B | RSS 订阅源（个人/共享分 scope） |
| GET / POST / PATCH / DELETE | `/api/schedules` | B | 日程 + 倒计时 |
| GET | `/api/system/metrics` | C | 硬件监控（Mac 阶段返回 mock JSON） |
| GET / POST / DELETE | `/api/vms` | C | VM 申请（Mac 阶段全 mock） |
| POST | `/api/vms/:id/upload` | C | 上传文件到 VM（mock） |
| GET | `/api/network/devices` | C | 局域网设备（mock） |
| WS | `/ws/events` | D | 事件总线，见 §3.3 |

**契约同步铁律**：
- 任何修改先改 `packages/contracts/openapi.yaml`，CI 自动生成 TS 类型 + Python pydantic 模型。
- PR 改动 OpenAPI 文件 → 必须三人 review。

### 3.2 SSE 流式协议（B → A）

`POST /api/chat/sessions/:id/messages` 的响应是 `text/event-stream`，事件类型如下：

```
event: session_started
data: {"session_id": "s_xxx"}

event: token
data: {"delta": "你好", "index": 0}

event: tool_call
data: {"id": "t1", "skill": "nas.list_recent", "args": {"limit": 5}}

event: tool_result
data: {"id": "t1", "ok": true, "summary": "找到 3 项"}

event: ui_action
data: {"type": "navigate", "to": "/feeds"}

event: done
data: {"message_id": "m_xxx", "tokens": 234}

event: error
data: {"code": "LLM_TIMEOUT", "message": "..."}
```

- **`ui_action`** 是"Agent 自己操作前端"的关键通道。A 在客户端注册 handler，B 通过此事件让前端切页 / 插组件 / 清屏。
- 所有事件都带 `message_id`，A 可断点重连。

### 3.3 WebSocket 事件总线（C/D → A，A → C）

`/ws/events` 双向，消息均为 JSON（完整定义见 `packages/contracts/ws-events.schema.json`）：

```jsonc
// C → A：唤醒
{"type": "wake", "user_id": "u_zhang", "confidence": 0.92}

// C → A：识别到人脸位置（用于前端可视化）
{"type": "face_track", "x": 0.42, "y": 0.31, "size": 0.18}

// C → A：用户离开
{"type": "leave", "duration_ms": 12000}

// A → C：请求屏幕旋转（Mac 阶段：no-op + 日志）
{"type": "rotate_screen", "orientation": "portrait"}

// A → C：请求开始 / 停止人脸跟踪
{"type": "tracking", "enabled": true}

// C → A（经 D 中转）：硬件指标实时推送
{"type": "metrics_update", "payload": { "ts": "...", "cpu_cores": [...], ... }}

// C → A：屏幕方向已变更
{"type": "screen_changed", "orientation": "portrait"}
```

### 3.4 Skill 接口（B + C 共建）

每个 Skill 是 `packages/skills/<name>/` 下的目录，含：

- `skill.md` — YAML frontmatter + 自然语言描述（给 LLM 看）
- `handler.py` — Python 实现（被 Agent 调用）
- `schema.json` — 输入输出 JSON Schema
- `tests/` — pytest 单元测试 + 黄金样例

`skill.md` frontmatter 模板：

```yaml
---
name: nas.list_recent
version: 0.1.0
owner: C
scopes: [nas.read]
mac_mock: true       # Mac 阶段是否走 mock
inputs:
  limit: { type: integer, default: 10 }
  user_id: { type: string, optional: true }
outputs:
  items: { type: array }
risk: low            # low / medium / high
---
查询 NAS 最近存入的文件，可按用户过滤。
```

详细规范见 `02_AgentB_规划书.md` §5。

### 3.5 数据库 Schema（首版）

D 用 Alembic 维护迁移。核心表：

```sql
-- 用户与认证
users(id, username, display_name, password_hash, role, created_at)
user_preferences(user_id, key, value_json, updated_at)
user_face_embeddings(user_id, embedding bytea, source, created_at)  -- C 写入

-- 会话与记忆
chat_sessions(id, user_id, started_at, ended_at, scope)
chat_messages(id, session_id, role, content, tool_calls_json, created_at)
agent_memories(id, user_id, type, content, embedding, ts)            -- B 写入

-- 信息源
feeds(id, owner_id_or_null_for_shared, url, title, scope, config_json, created_at)
feed_items(id, feed_id, guid, title, summary_md, url, published_at, fetched_at)

-- 日程
schedules(id, user_id_or_null_for_shared, title, body, due_at, scope, created_by_agent, created_at)

-- 系统快照（Mac 阶段写 mock 数据）
system_metrics_snapshot(ts, payload_json)
vm_records(id, owner_id, name, cpu, mem_gb, disk_gb, status, created_at)  -- Mac 阶段 status 来自 mock
```

**Scope 字段**：`personal` / `shared` / `public`。所有按 scope 过滤的查询都走 D 的统一 helper，不允许各服务自己写 SQL。

## 4. Mock 协议（让四人独立跑起来的核心）

### 4.1 原则

> **"上游没好之前，永远有 Mock 让下游自测。"**

- 每个跨人接口都有 Mock 实现。Mac 阶段 Mock 默认开启，**LLM 除外**——LLM 默认走真 MiniMax-M2.7 API，仅 `LLM_PROVIDER=mock` 时切回声。
- Mock 数据放 `services/<svc>/mocks/*.json`，由每个服务的 owner 维护。
- Mock 不是"返回空"，而是返回**真实形态、有变化的数据**（例如 `MOCK_NAS` 每次调用返回不同时间戳）。
- 集成测试时通过 env 切换为真实实现。

### 4.2 Mock 矩阵

| 接口 | Mock 拥有者 | Mock 形态 |
|---|---|---|
| LLM `MiniMax-M2.7` | B | 本地确定性回复器（按 prompt 关键词匹配返回固定脚本） |

### 5.3 Git 版本管理规范

> **本节是所有 Git 操作的唯一权威。违反分支/提交/PR 规则 = 构建失败或强制回退。**

#### 5.3.1 分支策略（轻量 Git Flow）

```
main          ← 生产分支，永远可部署。直接 push 禁止，只接受 PR 合并。
  │
  ├── develop  ← 集成分支（可选，<4 人用 main 收 PR 即可）
  │
  ├── a/<topic>   ← A 的个人分支（feat/web/..., fix/web/...）
  ├── b/<topic>   ← B 的个人分支（feat/agent/..., fix/agent/...）
  ├── c/<topic>   ← C 的个人分支
  ├── d/<topic>   ← D 的个人分支
  │
  └── release/v0.x   ← 发布分支（冻结后只修 bug）
```

**分支命名规则**：

| 前缀 | 用途 | 示例 |
|------|------|------|
| `a/` `b/` `c/` `d/` | 个人日常开发 | `a/feat-chat-stream-render` |
| `feat/` | 跨人特性分支（临时） | `feat/sse-reconnect` |
| `fix/` | 修 bug | `fix/ws-leak-on-disconnect` |
| `release/v*` | 发布冻结 | `release/v0.1.0` |
| `hotfix/` | 生产紧急修复 | `hotfix/jwt-expire-panic` |

**铁律**：
- **永远不直接 push 到 main**。main 只接受 PR 合并。
- 个人分支命名必须带 `{a,b,c,d}/` 前缀，防止四人分支池混乱。
- 一个分支只做一件事。禁止"顺手修了另一个模块的 bug"——另开分支。
- 分支在合并后 24h 内删除（由 merge author 负责）。

#### 5.3.2 Commit 规范（Conventional Commits）

```
<type>(<scope>): <subject>
^────^^───────^  ^──────────────────^
│     │          │
│     │          └─ 50 字以内的英文摘要，小写开头，不加句号
│     └─ scope：web / agent / perception / gateway / skills / contracts / infra / docs
└─ type：
    feat     = 新功能
    fix      = 修 bug
    refactor = 重构（不改行为）
    test     = 加测试
    docs     = 文档
    chore    = 构建 / CI / 依赖
    perf     = 性能优化
    revert   = 回滚
    style    = 格式（仅空格/分行，不碰逻辑）

Body（可选）：72 字换行，写 Why 不写 What。
Footer（可选）：BREAKING CHANGE: ... 或 Closes #123
```

**示例**：

```
feat(web): add streaming markdown render for chat bubble

fix(agent): prevent SSE double-close on client disconnect

chore(infra): bump postgres image to 16.4
```

**强制执行**：commit-msg hook 用 `commitlint` 检查格式。不合规 = 提交被拒。

#### 5.3.3 PR 流程

**PR 模板**（`.github/PULL_REQUEST_TEMPLATE.md`）：

```markdown
## 变更摘要
<!-- 一句话说明 Why -->

## 变更类型
- [ ] feat / [ ] fix / [ ] refactor / [ ] test / [ ] docs / [ ] chore

## 测试
- [ ] 新代码有单测且通过
- [ ] 集成测试通过
- [ ] E2E 通过（UI 改动必跑）
- [ ] 覆盖率不降

## 影响面（必勾）
- [ ] 改了 OpenAPI（`packages/contracts/openapi.yaml`）→ 需三人 review
- [ ] 改了 DB schema → 附 alembic up + down 截图
- [ ] 改了 Dockerfile → 附 build 通过截图
- [ ] 改了 .env.example → 已通知全员
- [ ] 新增依赖 → 已评估国内可达性 + 体积
- [ ] Mock 数据有变 → 已更新对应 fixtures

## 截图 / 录屏（UI 改动必附）
```

**Review 规则**：

| 改动范围 | 最少 reviewer 数 | 谁 |
|---------|------------------|-----|
| 自己模块内（apps/web, services/agent 等） | 1 | 任一人 |
| `packages/contracts/` | **3** | 全员 |
| `infra/db/migrations/` | 2 | D + 任一人 |
| `infra/docker/` 或 `infra/compose/` | 2 | D + 任一人 |
| `docs/`（不含 ADR） | 1 | 任一人 |
| `docs/adr/` | 3 | 全员 |

**合并策略**：Squash & merge。合并 commit message 用 PR 标题 + `(#PR编号)`。

#### 5.3.4 Git Hooks（pre-commit + commit-msg）

#### 5.3.6 Tag 与 Release


- **Tag 打在 main 上**，不打在个人分支。

#### 5.3.7 日常工作流

```bash
# 1. 从最新 main 开始
git checkout main && git pull origin main

# 2. 开个人分支
git checkout -b a/feat-chat-bubble

# 3. 开发 + 频繁小 commit
git add apps/web/src/features/chat/ChatBubble.tsx
git commit -m "feat(web): add ChatBubble component"

# 4. 自测后 push
git push origin a/feat-chat-bubble

# 5. 开 PR → review → 通过 → Squash merge

# 6. 清理
git checkout main && git pull origin main
git branch -d a/feat-chat-bubble
```

#### 5.3.8 冲突解决

- **同文件冲突**：两人各自开分支，先到先合；后合的人负责解决冲突。
- **contracts 冲突**：必须把两人拉到一起，共同在屏幕前解决；不允许单方面覆盖。
- **数据库迁移冲突**：后合的人必须把自己的迁移 rebase 到最新 head 之后，重拍 alembic 版本号。

#### 5.3.9 回滚与事故

| 场景 | 操作 |
|------|------|
| 刚合并的 PR 出问题 | `git revert <merge-commit>` + PR review |
| 生产部署后发现问题 | `./infra/scripts/rollback.sh v0.0.9` + 回滚 db（如有不可逆迁移） |
| 误删分支 | `git reflog` → `git checkout -b <lost-branch> <sha>` |
| 敏感信息误提交 | `git filter-branch` 或 `BFG Repo-Cleaner` → 轮换所有泄露的 secret → force push（需全员下线） |

## 6. 测试规范（全员通用）

> 详细的、按角色细化的测试要求，写在各自规划书的"测试规范"章节。这里只列**全员共同基线**。

### 6.1 测试目录结构（每人独立）

```
tests/
├── A/                           # A 的测试（前端）
│   ├── unit/                    # Vitest + RTL
│   ├── integration/             # MSW + 组件集成
│   ├── e2e/                     # Playwright
│   └── visual/                  # 截图对比（Chromatic / Playwright snapshot）
├── B/                           # B 的测试（Agent + LLM）
│   ├── unit/                    # pytest
│   ├── integration/             # testcontainers PG/Redis
│   ├── golden/                  # LLM 问答黄金集 .jsonl
│   └── perf/                    # 延迟 / 并发 / token 速度
├── C/                           # C 的测试（Perception + 外设）
│   ├── unit/                    # pytest + OpenCV mock
│   ├── integration/             # 假摄像头视频 / 串口 mock 回环
│   ├── fixtures/                # 测试视频 / 假摄像头帧 / 人脸样本
│   └── model_regression/        # 人脸识别率 / 误识率 周跑
└── D/                           # D 的测试（基础设施 + 数据）
    ├── unit/                    # pytest
    ├── integration/             # testcontainers + Docker Compose test
    ├── contract/                # schemathesis fuzz
    └── security/                # 上传 Fuzz / SSRF / 注入 / 依赖扫描
```

**原则**：
- 每个人在自己目录下独立组织测试，互不侵入。
- 跨人测试（E2E / 契约 / 安全）放在主导者的测试目录下。
- CI 各人测试目录**并行跑**，单份不超过 5 分钟。

### 6.2 测试金字塔

```
            ┌──────────────────────┐
            │  E2E (Playwright)    │  tests/A/e2e/
            ├──────────────────────┤
            │  契约测试             │  tests/D/contract/
            ├──────────────────────┤
            │  集成测试 (pytest)    │  tests/{A,B,C,D}/integration/
            ├──────────────────────┤
            │  单元测试             │  tests/{A,B,C,D}/unit/
            └──────────────────────┘
```

### 6.3 共同标准

- **覆盖率门槛**：单元 ≥ 70%，关键模块（鉴权 / Skill 调度 / SSE） ≥ 90%。
- **CI 必过**：lint + typecheck + 单元 + 契约。E2E 在 nightly 跑。
- **PR 准入**：新代码必须带测试。修 bug 必须先写复现测试。
- **黄金样例**：LLM 输出维护 `tests/B/golden/*.jsonl`，每周回归对比。
- **测试命名**：`test_{模块}_{场景}.{ext}`，如 `test_nas_list_recent_mock.py`。
- **测试不碰生产**：任何测试不允许连生产数据库 / 真 API Key / 真 MiniMax 配额（标 `@pytest.mark.live` 除外，CI 不跑）。
- **Fixture 就近放**：谁用谁维护，放在对应测试目录下的 `conftest.py` 或 `fixtures/` 中。
- **每个人的测试跑自己的 CI job**：`test-a` / `test-b` / `test-c` / `test-d` 四个 job 并行跑，互不等待。

### 6.3 性能基线（Mac 阶段验收）

| 指标 | 目标 |
|---|---|
| API p95 延迟（非 LLM） | < 200ms |
| LLM 首 token 延迟 | < 1500ms（云 MiniMax） |
| LLM token 间隔 | < 80ms |
| WS 事件端到端延迟 | < 100ms |
| Web 首屏 LCP | < 2s |

### 6.4 安全基线

- 任何用户输入到 LLM 之前先做 prompt-injection 扫描（B 实现 `safety.guard`）。
- Skill 执行白名单（B），危险 Skill（risk: high）需二次确认。
- 上传文件大小、类型、路径校验（D）。
- JWT 短 TTL + 刷新 token；密码 bcrypt。
- 依赖每周 `pnpm audit` / `pip-audit`。

## 8. AI 协作约定（四人共用）

每人都会用 AI（Claude / Cursor / Copilot）协作。共同约定：
