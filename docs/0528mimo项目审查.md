## 三、阻塞发布的关键问题

### 3.1 大量 `" 2"` 重复文件（约 20+ 个）

几乎每个目录都有带空格+数字后缀的副本，是合并/复制产生的垃圾文件。

| 模块 | 重复文件示例 |
|------|-------------|
| `infra/db/versions/` | `002_user_profile_extension 2.py` ~ `010_page_monitor 2.py` |
| `services/perception/app/core/speech/` | `speech 2.py`, `speech 3.py`, `speech 4.py` + 同级 `__init__`, `base`, `funasr_engine`, `mock` 的 2/3/4 副本 |

**风险**: 可能引发 import 混乱、打包体积膨胀、IDE 索引错误。

### 3.2 `admin-cli` 是空壳

`apps/admin-cli/` 只有 `.DS_Store`，没有任何实际代码。文档中列为 Role D（管理 CLI）的职责模块，完全未实现。

### 3.3 Logout 是桩实现

`services/api-gateway/app/api/auth.py:169` 标注 `TODO: add refresh token to Redis blacklist (W2)`。当前 logout 只返回 204，token 仍然有效。公共设备场景下存在安全风险。

### 3.4 OpenAPI 规范不完整

已实现但未写入 `openapi.yaml` 的端点：

## 十一、深度调查：前端 API 连通性审计

> 由 Explore agent 逐页面审计前端与后端的连接方式。

### 11.1 API 客户端

- **Base URL**: 硬编码为 `'/api'`（相对路径），依赖 Vite dev proxy 或同源部署
- **认证**: 每次请求从 `useAuthStore` 读取 `accessToken`，附带 `Authorization: Bearer`
- **CSRF**: 从 cookie 读取 `csrf_token`，非 GET 请求附带 `X-CSRF-Token`
- **401 处理**: 直接调用 `logout()`，**无 token 刷新逻辑** — `refreshToken` 存储在 auth store 但从未使用

### 11.2 SSE 客户端

- 使用 `fetch()` + streaming body reader（非 `EventSource`）
- **无重连机制** — 连接断开后需用户手动重发消息
- 支持事件类型：`token`、`tool_call`、`tool_result`、`ui_action`、`done`、`error`

### 11.3 WebSocket / EventBus

- 优先使用 `SharedWorker`（多标签页共享连接），降级到直接 `WebSocket`
- 连接地址：`ws://${location.host}/ws/events`
- **零认证** — 不携带 token、不转发 cookie、无 query param auth
- 指数退避重连（1s ~ 30s）

### 11.4 状态管理

| Store | 持久化 | 发现 |
|-------|--------|------|
| `auth.ts` | localStorage (zustand persist) | token 存 localStorage，XSS 风险；`refreshToken` 从未使用 |
| `session.ts` | 仅内存 | 纯 UI 状态 |
| `ui.ts` | 仅内存 | Toast 通知 |
| `connection.ts` | localStorage | 服务器状态追踪 |

### 11.5 逐页面连通性

| 页面 | API 调用 | MSW 覆盖 | Loading/Error 状态 |
|------|---------|---------|-------------------|
| StudioHomePage | `/weather`, `/schedules`, `/feeds`, `/vms`, `/chat/sessions`, SSE | **weather 无 mock handler** | 有 skeleton + error + retry |
